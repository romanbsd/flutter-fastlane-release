# Flutter Fastlane release lanes

Shared, app-neutral Fastlane lanes for Flutter apps. This repository contains no
app identifiers, credentials, signing material, store metadata, or release notes.
Each application imports a pinned Git submodule commit and keeps those values in
its own repository or environment.

## Install in an app

```sh
git submodule add https://github.com/romanbsd/flutter-fastlane-release.git vendor/flutter-fastlane-release
```

In the app's `fastlane/Fastfile`:

```ruby
import '../vendor/flutter-fastlane-release/Fastfile'
```

Keep a root `Gemfile` and lockfile with Fastlane, an app-specific
`fastlane/Appfile`, and `fastlane/.env.example`. CI must use
`git submodule update --init --recursive` before Bundler/Fastlane.

## Lanes

| Lane | Purpose |
|---|---|
| `beta_preflight` | Read-only check of numbers, stores, signing and toolchain; previews `bump:` |
| `beta_all` | Analyze, test, build and upload both platforms |
| `ios beta` / `android beta` | The same release for one platform |
| `ios build` / `android build` | Build only; explicit build number required; never edits pubspec |
| `ios upload ipa:<path>` / `android upload aab:<path>` | Upload an existing artifact; needs a receipt or `sha256:<digest>` |
| `ios distribute` | Redistribute an existing TestFlight build |
| `ios release` | Submit an existing build for App Review (`IOS_RELEASE_MODE=app_store_submission`) |
| `ios firebase_beta` / `android firebase_beta` | Ad hoc build via Firebase (`ENABLE_FIREBASE_DISTRIBUTION=true`) |
| `android store_listing` | Upload Play metadata and images without a build |
| `android screenshots serial:<adb serial>` | Capture Play phone screenshots on an emulator (see below) |
| `draft_release_notes build_number:<n>` | Draft notes without committing them |
| `bump_build_version build_number:<n>` | Raise the pubspec build without deploying |
| `test` | `flutter analyze` and `flutter test` |

## Beta release

### Build numbers and commits

A beta release lane with no `IOS_BUILD_NUMBER` or `ANDROID_BUILD_NUMBER` assigns
the next build itself: one above the latest build already on the stores being
shipped, and never below the pubspec build. The beta lanes write the selected
build — automatic or explicit — to `pubspec.yaml` and commit it together with
any generated changelog before building. A combined release uses the lowest
selected build so both artifacts are at or above the pubspec build.

Explicit numbers must already exceed the store and never go below the pubspec
build. When every number is explicit, the matching notes must already be
committed, unless a version bump is requested (the new version's notes are
generated). A mixed release generates missing notes for the override.

`PLAY_STORE_VALIDATE_ONLY=true` changes nothing in the repository, so it requires
an explicit platform build number. Run one release at a time: two concurrent runs
can assign the same build. A failed build leaves the pubspec/changelog commit in
place; the next run starts from that committed build rather than rolling it back.

### Release notes

Notes live at `fastlane/release_notes/<version>+<build>.txt`, are limited to 500
characters, and reused builds must use the committed bytes. Missing notes are
generated by Codex: the Codex CLI must be installed and authenticated, and
generation is bounded by `CODEX_NOTES_TIMEOUT_SECONDS` (default 300).
`RELEASE_NOTES_FROM` and `RELEASE_NOTES_TO` can pin the analyzed revision range.
`draft_release_notes` writes a file for review without committing it.

### Version bumps

Bump the version as part of the release with the `bump:` option, or set
`VERSION_BUMP` (a lane option wins over the environment):

```sh
bundle exec fastlane beta_all bump:minor
VERSION_BUMP=patch bundle exec fastlane ios beta
```

`major` resets minor and patch to zero, `minor` resets patch, and any pre-release
suffix is dropped. The version and build are written and committed in one
`Release x.y.z+build.` commit, and notes are generated for the new version.
`bump:` is accepted by the iOS and Android beta lanes, their TestFlight/Android
aliases, `beta_all`, and `beta_preflight` (preview only). Build-only and Firebase
lanes ignore version bumps, and `PLAY_STORE_VALIDATE_ONLY` rejects them.

### Release tags

After a successful upload, the beta lanes (`beta_all`, `ios beta`, `android beta`
and their TestFlight/Android aliases) create a local `vX.Y.Z` git tag when the
release is a new major.minor.patch version. A tag is skipped when it already
exists, when the version is not newer than the latest `v*` tag on `HEAD`, for
pre-release versions such as `1.2.0-rc`, and for build-only or validate-only
runs. Retries are idempotent. Tags are not pushed automatically: use
`git push origin vX.Y.Z` (or `git push --tags`). Upload lanes and App Store
submission assume a beta lane already tagged the version.

### Running and retries

Run `bundle exec fastlane beta_preflight`, then `bundle exec fastlane beta_all`
for a combined release, or `ios beta` / `android beta` separately. Preflight
computes and validates the next numbers (stores, signing, toolchain, notes for
explicit releases without a bump), previews `bump:` in its output, and writes
nothing; `beta_all` assigns the numbers again. `beta_all` runs `flutter analyze`
and `flutter test` before building.

Each run records itself in `build/release/status.json`, and every built artifact
gets a receipt in `build/release/receipts.json` keyed by version and build, so a
receipt survives a later attempt that fails before building. An upload
interruption can leave an unknown store outcome: check the store before retrying.
`ios upload ipa:<path>` and `android upload aab:<path>` read the embedded
version/build and require a matching receipt or an explicit `sha256:<digest>`,
plus the matching committed notes.

### Stores, signing and platforms

Android beta accepts only `internal`, `alpha`, or `beta` via
`PLAY_STORE_BETA_TRACK`. `android store_listing` uploads Play metadata and
optional images only; it targets `PLAY_STORE_VERSION_CODE` (or
`SUPPLY_VERSION_CODE`) and otherwise the latest release on the track. Changelogs
are uploaded only for an explicit version code.

TestFlight distribution uses `TESTFLIGHT_GROUPS` and
`TESTFLIGHT_DISTRIBUTE_EXTERNAL`. For external testing, also provide the
app-specific `TESTFLIGHT_BETA_APP_DESCRIPTION` and
`TESTFLIGHT_BETA_APP_FEEDBACK_EMAIL`, and complete beta review
contact/demo-account details in App Store Connect. External builds may require
Apple's beta review before testers can install them.

The current App Store upload minimum is Xcode 26 with an iOS 26 SDK, and Google
Play updates must target Android API 36 or later; verify current store
requirements before each release. Android release builds need
`android/key.properties` (`storeFile`, `storePassword`, `keyAlias`,
`keyPassword`) or `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS`, and `ANDROID_KEY_PASSWORD`. The app Gradle `release`
build type has to use that keystore. A Flutter template that leaves
`signingConfig signingConfigs.debug` still produces a debug-signed bundle
after the credential check passes. `storeFile` is resolved by the app's Gradle
file, commonly from `android/app`.

iOS signing uses read-only `match`;
`APPLE_TEAM_ID` and pre-provisioned signing assets are required. Manual signing
settings are applied to the `Runner` target only, so apps with extension targets
keep their own signing configuration in the Xcode project. The original
`project.pbxproj` is backed up as `project.pbxproj.fastlane-backup` before
signing changes and removed after a successful restore; if a run is killed,
restore it manually. `APP_STORE_CONNECT_API_KEY_PATH` is required in CI.

App Store submission is a separate `ios release` lane, enabled by the app's
`IOS_RELEASE_MODE=app_store_submission` setting; it selects an existing build and
releases manually after approval. Notes are written for
`APP_STORE_NOTES_LOCALE` (default `en-US`). Apps that previously used
`ios release` for TestFlight can set `IOS_RELEASE_MODE=testflight_alias`;
`ANDROID_RELEASE_MODE=beta_alias` likewise retains an Android beta alias.
`ENABLE_FIREBASE_DISTRIBUTION=true` enables the Firebase lanes; they require the
app's Firebase config, an explicit platform build number, committed notes, and
the Fastlane Firebase plugin. `ios firebase_beta` builds an Ad Hoc export so
testers can install the IPA directly. App Store submission and Firebase
distribution remain opt-in.

## Settings

| Setting | Effect |
|---|---|
| `IOS_BUILD_NUMBER`, `ANDROID_BUILD_NUMBER` | Reuse a specific build; must exceed the store and the pubspec build |
| `bump:` lane option, `VERSION_BUMP` | `major`, `minor`, or `patch` version bump |
| `FLUTTER_CLEAN=true` | Run `flutter clean` before `flutter pub get` |
| `ALLOW_DIRTY=true` | Skip the clean-worktree requirement |
| `CODEX_NOTES_TIMEOUT_SECONDS` | Release-notes generation timeout (default 300) |
| `NOTES_BUILD_NUMBER` | Build drafted by `draft_release_notes` when its option is omitted |
| `RELEASE_NOTES_FILE` | Alternate notes path inside the application repository |
| `RELEASE_NOTES_FROM`, `RELEASE_NOTES_TO` | Revision range passed to Codex |
| `PLAY_STORE_BETA_TRACK` | `internal`, `alpha`, or `beta` |
| `PLAY_STORE_RELEASE_STATUS` | `completed`, `draft`, `halted`, or `inProgress` |
| `PLAY_STORE_ROLLOUT` | Staged rollout fraction, greater than 0 and at most 1 |
| `PLAY_STORE_VALIDATE_ONLY` | Validate the Play edit; no release and no repository change |
| `PLAY_STORE_LISTING_TRACK` | Track used by `store_listing` (default `production`) |
| `PLAY_STORE_VERSION_CODE` / `SUPPLY_VERSION_CODE` | Release targeted by `store_listing` changelogs |
| `PLAY_STORE_UPLOAD_IMAGES`, `PLAY_STORE_UPLOAD_SCREENSHOTS` | Include images/screenshots in `store_listing` |
| `TESTFLIGHT_GROUPS`, `TESTFLIGHT_DISTRIBUTE_EXTERNAL` | TestFlight distribution |
| `TESTFLIGHT_BUILD_NUMBER` | Build redistributed by `ios distribute` when its option is omitted |
| `TESTFLIGHT_BETA_APP_DESCRIPTION`, `TESTFLIGHT_BETA_APP_FEEDBACK_EMAIL` | Required for external TestFlight |
| `TESTFLIGHT_NOTIFY_EXTERNAL_TESTERS` | Notify external testers |
| `APP_STORE_CONNECT_API_KEY_PATH` | App Store Connect API key; required in CI |
| `APP_STORE_ID`, `APPLE_TEAM_ID` | iOS build defines and signing team |
| `USES_NON_EXEMPT_ENCRYPTION` | Export-compliance fallback when the IPA/Info.plist omits it |
| `APP_STORE_VERSION`, `APP_STORE_BUILD_NUMBER` | Build selected by `ios release` |
| `APP_STORE_NOTES_LOCALE` | Locale for App Store release notes (default `en-US`) |
| `IOS_RELEASE_MODE`, `ANDROID_RELEASE_MODE` | Enable the `release` aliases |
| `ENABLE_FIREBASE_DISTRIBUTION` | Enable the Firebase lanes |
| `FIREBASE_IOS_GROUPS`, `FIREBASE_ANDROID_GROUPS` | Firebase tester groups (default `beta-testers`) |
| `GOOGLESERVICE_INFO_PLIST_PATH` | iOS Firebase config path |
| `PLAY_SCREENSHOTS` | Comma-separated screenshot names `android screenshots` must capture |
| `PLAY_SCREENSHOTS_TEST`, `PLAY_SCREENSHOTS_LOCALE` | Screenshot driver (default `integration_test/store_screenshots_test.dart`) and metadata locale (default `en-US`) |
| `APP_IDENTIFIER` | Bundle ID for the App Store tools when the Appfile computes it |
| `BUNDLETOOL_JAR` | bundletool JAR used to read AAB metadata |

## Store screenshots

### Google Play

`android screenshots` runs the app's screenshot driver on an attached emulator or
device and writes `fastlane/metadata/android/<locale>/images/phoneScreenshots/`,
which `android store_listing` uploads. The display is switched to 1080 x 1920
(Play rejects anything taller than 2:1) with a clean demo status bar, then reset.

The app provides `integration_test/store_screenshots_test.dart`: seed demo data,
navigate, wait for each screen's content, then print `PLAY_SHOT <name>` and hold
the screen for about three seconds. Every marker becomes `<name>.png` from a real
`adb screencap`, so blur and shaders render exactly as on a phone. The committed
set is replaced only when every name in `PLAY_SCREENSHOTS` was captured.

```ruby
# fastlane/Fastfile, before the import
ENV['PLAY_SCREENSHOTS'] ||= '01-home,02-detail,03-settings'
```

### App Store Connect

Standalone tools run from the app root with its `fastlane/.env` and Appfile
`app_identifier` (or `APP_IDENTIFIER`). Each defaults to a read-only plan:

```sh
bundle exec ruby vendor/flutter-fastlane-release/tools/app_store_status.rb
bundle exec ruby vendor/flutter-fastlane-release/tools/app_store_screenshots.rb --version 1.2.0 --build 21 [--upload]
bundle exec ruby vendor/flutter-fastlane-release/tools/app_store_release_mode.rb --version 1.2.0 --build 21 --mode manual [--apply]
bundle exec ruby vendor/flutter-fastlane-release/tools/upload_existing_ios.rb --ipa build/ios/ipa/App.ipa --version 1.2.0 --build 21 [--upload]
```

`app_store_screenshots.rb` uploads every PNG in
`fastlane/screenshots/en-US/iphone-medium/` (1206 x 2622) and `ipad/`
(2064 x 2752) to a Prepare for Submission draft whose selected build matches,
validates headers and Apple upload targets first, never deletes screenshots,
and is safe to rerun.

## Verification and upgrades

Run `bundle exec ruby test/release_check.rb` and `bundle exec ruby test/app_store_tools_check.rb` in this repository. Dependabot
checks the standalone test bundle and CI actions weekly; review its PRs and
the passing CI job before merging. Before
updating the submodule pin, review the shared commit range, run this test, and
run `bundle exec fastlane lanes` plus each app's release checks. Update the
submodule in each app through its master branch. No store upload is part of the
shared component's own CI.
